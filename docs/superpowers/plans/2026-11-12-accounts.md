# Accounts Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A new Accounts menu in the Solarize CRM: payments received and pending (with WhatsApp reminders), receipts and the final tax bill as PDFs shared with the customer or the loan bank, a per-project cost sheet with a reusable materials list and a printable material list, company expenses, and profit.

**Architecture:** One new PHP module `api/accounts.php` (module `acc`) owns all new tables and the shared money rules (pending, bill lock, profit), reusing the existing `payments`, `projects`, `gen_docs`, `fees`, `commissions` and `ad_spend` tables. The browser side is a pure, Node-tested rules module (`ACC`, app32.js) plus three UI files, built in this order: receipts / sharing / email + the Tax bill tab lock (app35.js, Task 5), the Accounts page router + cost sheet + materials + material-list PDF (app33.js / app34.js, Task 6), then the Accounts list tabs (app33.js, Task 7). PDFs are made in the browser with the vendored jsPDF (+ html2canvas for receipts and the tax bill).

**Tech Stack:** PHP 8.3 + SQLite (PDO), vanilla JS (no build), jsPDF 2.5.1 + html2canvas 1.4.1 (`assets/vendor`), Node `node:test`, PHP API tests over curl.

**Spec:** `docs/superpowers/specs/2026-11-12-accounts-design.md` (read it first; section numbers below are its §).

## Global Constraints

- `SCHEMA_VERSION` 41 → **42** in `api/lib.php`; every new table/column is created in `migrate()` (idempotent) with an index on each filter column.
- Every POST carries header `X-Solarize: 1` (app's `api()` does this; tests must add it).
- The api.php GET whitelist is **by action name for every module**. New GET actions use the unique prefix `ac_` (`ac_overview`, `ac_pending`, `ac_received`, `ac_profit`, `ac_cost`, `ac_materials`, `ac_expenses`, `ac_tpl`, `ac_receipt`) and are added to that whitelist. Never whitelist a generic name (e.g. `cost`) — `gen/cost` is a write.
- Deletes go through the Recycle bin: call `trash_put(...)` before deleting (`api/trash.php`).
- Strict CSP: no inline scripts or `on*=` attributes; bind handlers in JS.
- New CSS lives in `assets/acc.css`, classes prefixed `.acx` (grep app.css/app2.css/quote.css/kseb.css first: must be unused).
- New scripts are added to `index.html` before `app13.js`; bump every `?v=` stamp on deploy (pattern `assets/(app[0-9]*|quote|kseb|acc)\.(js|css)`).
- Never real customer data in tests (made-up names, phones `90000000xx`).
- Money: two decimals, Indian grouping in the UI (`inr()` / `inr2()` exist).
- Before-GST divisor for a price with no tax bill: **1.089** (the CRM's 70:30 rule, 5% / 18%).
- Lint before each commit: `php -l <file>` and `node --check <file>`. Commit identity: `git -c user.name="Jasper Solar" -c user.email=gotjobinmilkwater@gmail.com commit …`, message ending with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- Test commands: `node --test tests/` and `bash tests/run_api.sh` (PHP at `C:\Users\gotjo\AppData\Local\Microsoft\WinGet\Packages\PHP.PHP.8.3_Microsoft.Winget.Source_8wekyb3d8bbwe\php.exe` when `php` is not on PATH).

## Review Focus

1. A loan project whose **loan amount is blank** or larger than the project price: the bill stays locked with "Enter the loan amount on the Bank & loan page" (blank) or treats the customer's share as 0 (loan ≥ price) — never a negative share or a crash.
2. **Overpaid** projects (payments > price): pending shows ₹0 (never negative), the project leaves the pending list, the bill unlocks.
3. A payment **deleted or edited** after its receipt was shared: totals recompute; share log rows stay (history), the receipt keeps its number.
4. **Customer with two projects**: a payment on the older project appears in Accounts lists and makes its own receipt; the Tax bill tab still uses the latest project only.
5. A cost sheet **saved from two tabs**: the later save replaces the lines wholesale (no merged duplicates); the materials list never gets two items with the same group + name (case-insensitive).

Each line has its test in the owning task (Tasks 2, 3, 4).
